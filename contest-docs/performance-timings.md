# Performance Timing Ledger

This file is the durable timing log required by `AGENTS.md`. It records wall
times observed while developing the AArch64 compiler; it is not a contest
score estimate.

## Measurement convention

Unless a row says otherwise, measurements were made on 2026-07-11 or
2026-07-12 on the Linux AArch64 Multipass VM hosted by the project Mac, reached
through `ssh wsy@192.168.1.106`. Programs were pinned with `taskset -c 0,1`,
linked with the official SysY runtime, and checked against their exact expected
output. Times are elapsed seconds reported by `/usr/bin/time` or the SysY
timer. "Sequential" means the same compiler invocation with
`--no-parallel-native`; it does not mean `-O0` unless explicitly stated.

Only rows in the same table section and marked as a paired comparison should
be used to calculate a speedup. Host load varied substantially between
sessions, so, for example, a 24.19-second MYO run must not be compared directly
with a 23.33-second run from the later peephole session.

## 2026-07-11: parallel and backend baselines

These measurements were taken from development worktrees that were later
consolidated in `f4e3ee2c` (and its equivalent contest-history commits). Each
subsection is a separate profiling session.

### MYO initial parallel baseline

| Program | Variant | Time (s) | Context |
|---|---:|---:|---|
| `2025-MYO-20` | old compiler, native parallel disabled | 78.56 | exact output |
| `2025-MYO-20` | hardened native parallel | 33.14 | paired with 78.56; 2.37x |
| `2025-MYO-20` | Clang `-O2` reference | 4.80 | reference ceiling, not compiler-to-compiler proof |

### MYO worker-shape experiment

| Program | Variant | Time (s) | Context |
|---|---:|---:|---|
| `2025-MYO-20` | repeated simpler inner worker | 31.30 | paired worker-shape experiment |
| `2025-MYO-20` | coarse outer worker with scratch-IV privatization | 36.04 | 15.1% slower than the inner worker |

The coarse result is why dynamic and large scratch-IV nests retain the simpler
inner worker; coarse scratch privatization is restricted to small constant
inner trip counts. An earlier report also compared 36.04 seconds with the
78.56-second sequential baseline (2.18x), but the two samples were under
different VM load and are not an incremental optimization comparison.

### Combined pipeline

|---|---:|---:|---|
| `2025-MYO-20` | combined optimizer, parallel disabled | 57.19 | paired with next row |
| `2025-MYO-20` | combined optimizer and native parallel | 24.19 | 2.36x versus 57.19; 3.25x versus the older 78.56 baseline |
| `2025-D6H-55` | before call-aware coverage | 13.35 | same-load A/B |

An earlier D6H A/B in a different session was also flat at 12.70 seconds for
both variants. Do not compare 12.70 directly with 13.35.

### Isolated backend optimizations

| Program | Change | Before (s) | After (s) | Result |
|---|---|---:|---:|---:|
| `2025-EB0-36` | injective `x19`-`x28` hot-temp residency | 4.988 | 3.470 | 1.44x |
| `2025-EB0-36` | hardened GVN plus CopyProp/DCE | 3.116 | 2.209 | 1.41x |

These are independent, paired experiments from different sessions and must
not be multiplied into a claimed end-to-end EB0 speedup. GVN/CopyProp also
reduced emitted AArch64 instruction count by 32.5% over the functional corpus.

Restricted scalar-int inlining was measured separately on `2025-4W1-32` over
ten samples: mean elapsed time fell from 112.357 ms to 110.492 ms (about 1.66%;
reported at the time as 1.69%). With native parallel disabled, the corresponding
means were 109.742 ms and 107.946 ms.

### Profitability-gate observations

For `2025-4W1-32`, a naive nested-work rule changed an approximately
0.11-second run into 0.20--0.25 seconds by creating a thread inside a repeated
outer loop. Loop-depth discounting restored the direct path. Other forced
threading probes on cheap reductions paid roughly 0.7--1.0 seconds of dispatch
overhead; these were tuning probes rather than retained configurations.

## 2026-07-12: clean pre-feature snapshot

This is one exact-output session from clean revision `bd2cf767`, before the
persistent pool, generalized strides, modular reductions, and bitwise idiom
specialization. Each sequential/parallel pair was generated by the same
compiler binary.

| Program | Sequential (s) | Native parallel (s) | Ratio | Voluntary switches, parallel |
|---|---:|---:|---:|---:|
| `2025-MYO-20` | 57.27 | 24.15 | 2.37x | 9,090 |
| `2025-NDT-1` | 57.27 | 24.16 | 2.37x | 8,327 |
| `2025-D6H-55` | 16.09 | 13.35 | 1.21x | 2 |
| `2025-680-52` | 5.95 | 5.96 | neutral | 1 |
| `2025-EB0-36` | 2.40 | 2.39 | neutral | 1 |
| `2025-4W1-32` | 0.12 | 0.12 | timer resolution | 2 |

The MYO/NDT parallel runs used about 0.4 seconds of system time. Their high
switch counts motivated the persistent helper, while the neutral 680/EB0/4W1
results showed that adding workers indiscriminately would not help.

Two uncovered sequential hotspots in the same clean-snapshot investigation
were `2025-O30-49` at 64.61 seconds and `2025-B3Z-8` at 49.21 seconds. They had
no valid parallel workers at that revision and motivated the modular and
bitwise features below.

## Persistent worker runtime (`dc3c3ec0`)

All comparisons below used retained pre-pool artifacts against the candidate
runtime later committed as `dc3c3ec0`.

### Sleeping-pool prototype (rejected)

| Program | Create/join samples (s) | Sleeping-pool samples (s) | Result |
|---|---:|---:|---|
| `2025-MYO-20` | 24.13, 24.12 | 24.51, 24.54 | about 1.7% slower |

Voluntary switches increased from 7,893/8,458 to 29,003/28,846 because every
dispatch slept on condition variables. This prototype was not retained.

### Adaptive pool (retained)

| Program | Create/join | Persistent adaptive pool | Result |
|---|---:|---:|---:|
| `2025-MYO-20` | 24.15, 24.14 s | 23.88, 23.85 s | means 24.145 -> 23.865 s; 1.17% faster |
| `2025-4W1-32`, 20 runs | 2.28 s total | 2.24 s total | about 1.8% faster |

MYO voluntary switches fell from 9,187/8,511 to 2,285/2,267 (about 74%). The
runtime combines short atomic spinning with condition-variable fallback and
uses direct execution for nested or concurrent re-entry.

## Exact modular reductions (`5aed7ffb`)

The retained implementation recognizes the exact integer recurrence and uses
a striped dynamic schedule. The final safety-refined A/B was:

| Program | Previous sequential (s) | Exact modular worker (s) | Result |
|---|---:|---:|---:|
| `2025-O30-49` | 64.51 | 33.05 | 1.95x |
| `2025-SFX-47` | 31.02 | 15.75 | 1.97x |

Earlier design probes, retained here to explain the scheduler choice:

| Program | Variant | Time (s) | Context |
|---|---:|---:|---|
| `2025-O30-49` | sequential wrapper | 64.88 | prototype session |
| `2025-O30-49` | contiguous midpoint split | 49.14 | exact but imbalanced; only 1.32x |
| `2025-O30-49` | striped/dynamic prototype | 33.38 | exact; 1.94x |
| `2025-SFX-47` | sequential baseline | 30.84 | same prototype session |
| `2025-SFX-47` | striped/dynamic prototype | 15.94 | exact; 1.94x |

The final runtime detects negative or overflow-risk addends and requests an
exact sequential retry; it does not silently reassociate unsafe signed
arithmetic.

## Guarded bitwise idiom (`94688a5b`)

These are alternating, exact-output A/B runs using each workload's own binary,
input, and output. The old variant is revision `0d8c6408`; the new variant is
the specialization later committed as `94688a5b`.

| Program | Original helper loops (s) | Guarded native idiom (s) | Speedup |
|---|---:|---:|---:|
| `2025-B3Z-8` | 50.30 | 2.97 | 16.94x |
| `2025-MOA-15` | 51.06 | 2.98 | 17.13x |
| `2025-OO6-21` | 53.32 | 2.97 | 17.95x |

An earlier clean-snapshot B3Z baseline was 49.21 seconds. Exact signed
power-of-two division alone reduced that artifact to 45.37 seconds (1.085x),
far less than recognizing the complete helper. Preliminary 2.48/2.50-second
MOA/OO6 probes reused a B3Z-built executable because the three sources were
identical; they were correctness-checked but are excluded from the canonical
table because the later experiment built each workload independently.

## Imported loop and AArch64 experiments

### LoopSimplify candidate (kept experimental)

On an isolated merge candidate based on `5aed7ffb` plus
`fj/feature/my-update`, `2025-EB0-36` had a 2.39-second median with
LoopSimplify disabled and a 2.71-second median enabled, a 13.4% regression.
The pass fired in only 6 of 60 performance programs and unrolled none in that
profile, so LoopSimplify and LoopUnroll remain opt-in.

### Textual AArch64 peephole (`0d8c6408`, now experimental)

Each cell lists three measured samples; the comparison differs only by
`SYSY_DISABLE_PASSES=peephole`. All outputs passed. The pass was still default
in isolated revision `0d8c6408`; it is no longer a default pass after
`94688a5b`.

| Program | Peephole enabled (s) | Peephole disabled (s) | Median effect |
|---|---:|---:|---:|
| `2025-B3Z-8` | 44.63, 44.63, 44.71 | 48.21, 48.58, 48.39 | 7.77% faster |
| `2025-EB0-36` | 2.29, 2.27, 2.26 | 2.34, 2.31, 2.33 | 2.58% faster |
| `2025-D6H-55` | 12.23, 12.20, 12.21 | 12.68, 12.68, 12.70 | 3.71% faster |
| `2025-680-52` | 5.88, 5.88, 5.89 | 5.62, 5.62, 5.61 | 4.63% slower |
| `2025-MYO-20` | 23.33, 23.23, 23.40 | 22.02, 22.08, 22.37 | 5.66% slower |
| `2025-O30-49` | 48.22, 31.35, 31.34 | 57.97, 31.56, 31.54 | noisy median about 0.7% faster |
| `2025-4W1-32` | 0.11, 0.10, 0.10 | 0.11, 0.10, 0.11 | below timer resolution |

The MYO and 680 regressions are why branch-removal text rewriting is gated.
Safe forms whose scratch lifetimes are known—pointer-plus-signed-offset and
comparison against literal zero—are instead constructed directly during
instruction selection and remain enabled. No standalone timing has yet
isolated only those construction-time forms.

Before the full seven-case run, a separate single EB0 probe of the imported
peephole candidate measured about 2.425 -> 2.385 seconds (1.65%). It is retained
as an exploratory result only; the repeated table above is the decision-grade
profile.

## SSA-aware GPR allocation (`6d6b856a`)

This clean-revision comparison used the Mac ARM64 VM, `taskset -c 0,1`, three
alternating rounds, a 300-second per-run timeout, and exact normalized output.
`default` is the SSA-aware live-interval allocator; `legacy` gives ten hot
temps function-long `x19`-`x28` homes; `off` is stack code.  Values are medians.

| Program | Default (s) | Legacy (s) | Off (s) | Default / legacy speedup |
|---|---:|---:|---:|---:|
| `matmul1` | 11.92 | 16.29 | 18.02 | 1.37x |
| `01_mm1` | 5.27 | 8.44 | 9.52 | 1.60x |
| `h-1-03` | 25.16 | 30.88 | 30.11 | 1.23x |
| `h-4-03` | 7.82 | 7.80 | 12.22 | neutral |
| `h-5-01` | 3.69 | 5.43 | 5.55 | 1.47x |
| `h-8-01` | 2.15 | 3.03 | 3.76 | 1.41x |
| `fft1` | 8.05 | 10.45 | 10.42 | 1.30x |
| `many_mat_cal-1` | 47.62 | 70.13 | 82.13 | 1.47x |
| `huffman-01` | 39.68 | 37.83 | compiler crash | 0.95x |
| `knapsack_naive-1` | 0.21 | 0.31 | 0.32 | 1.48x |

Across all ten default/legacy cases, summed time improves 190.59 -> 151.57
seconds (1.257x) and geometric-mean speedup is 1.311x.  Across the nine cases
where stack-code `off` compiled, summed time improves 172.05 -> 111.89 seconds
(1.538x), with 1.529x geometric mean.  Static all-60 analysis found temporary
stack accesses down 85.0% and total assembly instructions down 13.9%.

The `off` huffman failure is a compiler bug rather than a program result:
functions with more than four PHI copies need frame scratch slots after the
four dedicated snapshot registers, but the off-mode setup returned before
allocating those slots.  A five-PHI loop is the minimal reproducer.  Huffman's
repeatable roughly 5% default/legacy regression remains an allocator/codegen
tuning target.

## Updating this ledger

For every future performance run, append the date, compiler revision or dirty
worktree description, exact command/configuration, all samples (not only the
best), correctness status, and enough host context to decide which rows are
legitimately comparable. Prefer alternating A/B order and at least three
samples for long-lived decisions.
